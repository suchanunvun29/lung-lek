**Import-service integration — live-tested with a real `POST /import` call, and this is where a real defect was found.** Built a real 2-row `.xlsx` fixture (same column layout as `design.md`'s Import Rules — header row 2, `Product Name`/`Product type` columns) using `exceljs`, referencing an existing hospital/salesperson to isolate the test to product resolution: row A uses `"  pc-5  "` (whitespace/case variant of the already-aliased `"PC-5"`) but under `Product type = "C-cae"`, while the real `PC-5` product's actual `productTypeId` is `"GI"`; row B uses a brand-new product name never seen before, also under `"C-cae"`. Uploaded via `POST /import` as MANAGER → `201`, `insertedRows: 2`, `errorRows: 0`.

Querying the DB directly afterward: row B (the genuinely new product) is correct — new `Product(source=SALES_HISTORY, productTypeId=C-cae)` + new `ProductAlias(source=AUTO)`, no mismatch. Row A is **wrong**: `SalesLine.productTypeId` was set to `"C-cae"` (the row's raw file column) while the `Product` it resolved to (`PC-5`) has `productTypeId = "GI"` — `SalesLine.productTypeId != product.productTypeId`. Root cause, read in `productResolution.service.ts`: `resolveProductViaAlias`'s first lookup (`index.byAlias.get(key)`) is keyed only by the global `normalizedKey` — it does not consult or compare against the `productTypeId` argument at all, so once *any* alias exists for a name, every later row with that name resolves to that same `Product` regardless of what the current row's `Product type` column says. This directly contradicts `design.md`'s explicit, unconditional invariant at line 429 ("`SalesLine.productTypeId` เป็นการ denormalize จาก `Product` โดยตั้งใจ ... ตอน import ต้องเซ็ตให้ตรงกับ `product.productTypeId` เสมอ") — the code sets it from the file's raw column instead of from the resolved `Product`'s actual type.

Checked how much this matters against the real dataset before calling it: ran a direct SQL check (`GROUP BY name HAVING COUNT(DISTINCT "productTypeId") > 1` on `Product`, and a join comparing every `SalesLine.productTypeId` against its `Product.productTypeId`) — **zero** hits either way. No current `Product` name spans two types, and no existing `SalesLine` row is currently mismatched. So this bug has **not** corrupted any of the already-verified Phase 3/4 numbers today. But it is a real, reproducible code defect against a stated contract, not a hypothetical — it would trigger the moment a future import has a `Product type` typo or genuine cross-category name reuse for an already-aliased name, and the failure mode is silent (no `WARNING`/`ImportIssue` is raised) and would feed directly into Module D/E's `PRODUCT_GROUP` KPI and `TargetProductGroup` matching, which both read `SalesLine.productTypeId` directly (denormalized, no join) per `design.md`'s own stated reason for that denormalization.

When an already-aliased product name is imported again with a different `Product type` file value than the `Product` it's aliased to actually has, the row resolves to the existing `Product` (name match is correct) but `SalesLine.productTypeId` ends up set from the row's raw file column rather than from the resolved `Product`'s own `productTypeId` — breaking `design.md`'s explicit, unconditional invariant ("ตอน import ต้องเซ็ตให้ตรงกับ `product.productTypeId` เสมอ", line 429). Live-reproduced this round with a real `POST /import` call and confirmed via direct DB query; not present in the current 846-plus-test-row real dataset (checked directly — zero `Product` names span two types today), so no already-verified Phase 3/4 number is wrong *today*, but the bug is real, reproducible, and silent (no `WARNING`/`ImportIssue` raised), and would corrupt Module D/E's product-group KPI/target matching the moment it's triggered.

This is an **implementation bug**, not a design/schema gap or a business question: `design.md` already states the rule the code must follow ("ต้องเซ็ตให้ตรงกับ product.productTypeId เสมอ") unconditionally, and the fix — set `SalesLine.productTypeId` from the resolved `Product`'s own `productTypeId` rather than from `row.productTypeName`'s resolved id — doesn't require a new schema decision or a business call. (A secondary, genuinely open question `backend-engineer` should *not* try to resolve alone: whether a cross-type name collision like this should also raise a `WARNING`-level `ImportIssue` so a manager notices a mistyped `Product type` column — `design.md`'s Import Rules and Product Master & Ranking Rules are both silent on this specific case. If fixing the denormalization alone doesn't feel sufficient, that half should go to `system-analyst` rather than being decided in code.)

No other implementation bugs found. Migration, seed script, `GET`/`PATCH /products`, and the Zod schema all match `design.md`/`requirement.md` and passed every live test performed this round.
